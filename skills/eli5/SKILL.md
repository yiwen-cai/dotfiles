# eli5

## 受众识别
先从请求中判定受众：年龄、学段、职业角色或亲属关系。表述含糊时按最接近的一档处理，受众完全未提时默认「5 岁」。
各档的词汇、类比取材与关注点见 [audience-levels.md](references/audience-levels.md)，用到哪一档读哪一档，不整表套用。
同一请求出现多个受众（例如「给经理和工程师各讲一遍」）时分段输出，不混成一段折中表述。

## 材料准备
解释代码前读实际文件，不靠函数名猜行为；解释报错前定位根因，不复述错误文本；解释文档或概念前先抓出核心机制与因果。
材料不可得（文件缺失、日志不全、链接打不开）就说明缺什么，按已知部分解释，不虚构实现细节。
涉及本机项目时只读必要文件，不顺手修改代码。

## 解释与交付
默认结构：一句话说清「是什么」→ 一个受众熟悉的类比 → 按受众补必要细节 → 说明「对你意味着什么」。
非技术受众零术语，必须用的术语立刻解释；技术受众用准确术语并讲权衡与边界；业务受众先讲影响、成本与需要做的决定。
默认在对话里直接给文字解释。只有用户要图解、要可分享页面，或 `/eli5` 明确要求「图多字少」时才做 HTML 图解页面，此时遵循宿主的 artifact 规范。
准确度与可懂度冲突时可以牺牲精度，但要在结尾用一句话标出简化点，例如「这里把缓存层略掉了，真实链路还多一跳」。

## 边界
不居高临下：给 5 岁讲要有趣，给经理讲要可用于决策，不是降智。
不把解释变成执行：请求只是「讲清楚」时不顺带重构代码、跑实验或发消息。
受众判断不确定且影响很大（例如面向外部客户或正式材料）时先问一句，再按确认结果输出。
